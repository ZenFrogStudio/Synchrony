From a passing thought to a run that happened while you slept

Four steps, and you can join at any of them.

capture

Type one line into the Tasks sidebar. That is the whole step — a thought is not a plan yet.

generate

Claude reads the task, asks you what it needs, and writes a real plan into your library.

schedule

Pick a time and a repeat. Read the plan first — that is the safety step.

run

The window fires it, the terminal shows it live, and a transcript is written when it ends.

One tab, and everything is in it

Chronos is a single editor tab: your plan library on the left, detail on the right — schedule, working directory, permissions, the plan text itself — and run history along the bottom. Click the dragon in the activity bar to open it, or use the status bar item.

The working directory and the rolling seven-day cost are blurred in this capture. Everything else is a real window.

The Tasks inbox

The sidebar is a one-line inbox for work that is not a plan yet. Type it, press Enter, and it is captured — no tab switch between having the idea and writing it down.

A row's dot says what is happening to it: hollow while it is only captured, amber and pulsing while a planning session is open for it, green while a run started from here is in flight.

Generate plan opens a terminal running claude, already working from your task. It is an interactive session, not a headless one, so it can ask you anything it needs before committing to an approach. Approve the result and a real plan file lands in your library, the task disappears, and the manager opens with the new plan selected. Back out at any point and nothing is created.

Explain is the third button, and it writes nothing at all: it reads the task, looks around the project, and tells you in plain language what the change is, why it is needed, and what the alternatives are — including doing nothing. Reach for it when a task arrived from an agent as one line of somebody else's shorthand.

The plan library is a folder

A plan is a .md file in one directory, and that directory is the list. There is no index and no database, so editing a plan outside Chronos can never desynchronise anything, and deleting the file takes its schedule with it whether Chronos is open at the time or not.

A one-shot that runs successfully leaves the library for .chronos/archive/plans — it has no future once it has completed, though its run card and transcript stay under Runs. A plan that failed or was cancelled stays exactly where it is, visible, so you can fix it and run it again. Recurring plans never leave. Nothing in the archive is ever pruned.

Adding a plan always copies the file into the library and schedules the copy. Your original stays where it is and Chronos never edits or moves it — which also means editing your original afterwards will not change what runs.

Everything is per folder

Chronos keeps one set of tasks, plans, schedules and run history per folder, in a .chronos directory inside it. Open a project and you see that project's work and nothing else.

your-project/
  .chronos/
    plans/          your plan .md files
    tasks/          the task inbox
    archive/        plans and tasks that have left the library
    results/        run transcripts
    logs/           raw event streams
    state.json      schedules and run history
    scheduler.lock

The folder is ignored from git on creation — .chronos/.gitignore contains * — so edit that file if you would rather commit your plans. Two windows on two different projects both schedule independently.

Scheduling, and what happens while you are away

A plan runs once, daily, or on the weekdays you choose.

  • Missed windows wait for you. If the machine was asleep or VS Code was closed when a task was due, Chronos does not run it late. Past the grace window — 15 minutes by default — the occurrence is marked missed and waits for your decision: run it now, reschedule, or skip. A week-long outage collapses into one decision, not seven notifications.
  • Failed runs retry. One hour later, up to maxRetries attempts. Failures that retrying cannot fix — a deleted plan file, a missing working directory, a cancelled run — are not retried at all.
  • Recurrence survives daylight saving. It is stored as local wall-clock time, so "daily at 09:00" stays 09:00 across the transition. Concrete instants are derived from the rule, never accumulated.
  • A crash does not cost you a slot. A run left running because VS Code closed mid-flight is reconciled to failed at next launch and retried, rather than holding its concurrency slot forever.

Every run leaves a transcript

A scheduled job runs while you are away, so the record it leaves is the whole point. One folder per plan, one Markdown file per run, named by local start time and outcome — the folder tells you which nights went wrong before you open anything.

.chronos/results/
  nightly-audit/
    2026-07-26-213045-completed.md
    2026-07-27-213012-failed.md

Each file records the conditions the run executed under, the agent's narration, every tool call with its target, and a footer with the outcome, turns, cost and duration. The agent's closing message is kept on the run itself and shown in full in the manager's Runs section. Transcripts, unlike raw logs, are never deleted automatically.

Connect an agent over MCP

Chronos speaks the Model Context Protocol, so any MCP-capable agent — Claude Code, Codex, Cursor, Copilot — can drive the authoring half of the pipeline itself: capture a task, write it up as a plan, and put it on the schedule. The open VS Code window picks the schedule up and runs it that night.

claude mcp add chronos -- node "<launcher>" --folder "<project>"

There are 15 tools — seven that read and eight that write. Run Chronos: Copy MCP Server Config... from the command palette, pick your client, and paste what lands on the clipboard; eight clients each get the config shape they actually want.

The same server is how a planning session's questions can reach you on another device. Nothing leaves the machine to make that work: a question is a file in .chronos/questions and an answer is the same file written back, so the two ends never need a port, a token or an account between them.

An agent cannot set a permission mode. New tasks get the ordinary auto default, and raising one to bypassPermissions stays a decision you make in the manager, looking at a plan you have read. Asking for it over MCP is refused. There is also no "run now" tool — an agent sets a time and the window fires it, which keeps every run on the one path that has the concurrency cap, the watchdogs, the retry logic and the transcript machinery.

Read this before scheduling anything unattended

Chronos runs an AI agent while you are away from the machine. Three things follow from that.

  1. Tasks default to auto. Chronos runs plans with nobody at the keyboard, so the default leans on the CLI's own judgement about what is safe to do unattended rather than waiving permissions outright. The trade-off is that a mode which can still stop and ask has no one there to answer it at 3am, so a run may end having done only part of the job. Reviewing the plan before you schedule it is the safety step. bypassPermissions (full auto, unrestricted tool access — and one bad plan on a recurring schedule repeats indefinitely), acceptEdits (auto-approve edits, still gate shell commands) and plan all remain selectable per task.
  2. Runs cost money. A trivial prompt can cost ~$0.17 once context is loaded. A daily series with a broken plan bills every day until you notice. The manager footer shows a rolling 7-day total for exactly this reason.
  3. A run can "succeed" while doing less than you asked. If permission gating blocks tools, the run still exits 0. Chronos surfaces this as a ⚠ N denied badge rather than a silent success, and does not retry it — retrying would hit the same gate.

Building it yourself

npm install
npm run watch      # esbuild in watch mode
npm run typecheck
npm test           # pure-logic tests, no VS Code host needed
npm run package    # typecheck + bundle + vsce package

Press F5 to launch an Extension Development Host.

One honest limit

Chronos is an extension, not a daemon. A folder's tasks only run while a VS Code window is open on it. Tasks due while VS Code was closed are caught up, or marked missed, at next launch. For true machine-level scheduling you would want Windows Task Scheduler invoking claude directly.
